# Question 24

### **Question:**

**Can you explain how Kubernetes Ingress works?**

### **Answer:**

**Ingress** is a Kubernetes resource that manages **external HTTP/HTTPS traffic** and routes it to the appropriate application running inside the Kubernetes cluster.

A typical request flow looks like this:

```
User
   │
DNS
   │
Load Balancer
   │
Ingress Controller (NGINX)
   │
Ingress Rules
   │
Kubernetes Service
   │
Pods
```

Here's how it works:

1. The user accesses the application using a domain name.
2. DNS resolves the domain to the Load Balancer.
3. The Load Balancer forwards the request to the **Ingress Controller** (for example, NGINX Ingress).
4. The Ingress Controller reads the configured **Ingress rules**.
5. Based on the **host** or **URL path**, it routes the request to the appropriate Kubernetes **Service**.
6. The Service forwards the request to one of the healthy Pods.

For example:

```
api.company.com    → payment-service
admin.company.com  → admin-service
/app1              → app1-service
/app2              → app2-service
```

In our project, Ingress also handled:

* HTTPS termination using TLS certificates.
* Path-based routing.
* Host-based routing.
* Integration with external Load Balancers.

Ingress provides centralized traffic management instead of exposing every application separately.



# Question 25

### **Question:**

**Suppose a production application is down and a Pod is in CrashLoopBackOff state. What would be your first troubleshooting steps?**

### **Answer:**

My approach is to troubleshoot systematically instead of making changes immediately.

### Step 1 – Verify Pod Status

```bash
kubectl get pods -n <namespace>
```

Confirm which Pods are affected.



### Step 2 – Describe the Pod

```bash
kubectl describe pod <pod-name>
```

Check:

* Events
* Exit codes
* Probe failures
* Image pull issues
* Scheduling problems
* OOMKilled events



### Step 3 – Check Container Logs

```bash
kubectl logs <pod-name>
kubectl logs --previous <pod-name>
```

Since the container is restarting, the previous logs are often the most useful.



### Step 4 – Verify Configuration

Check:

* ConfigMaps
* Secrets
* Environment variables
* Mounted volumes
* Image version
* Startup command



### Step 5 – Verify Readiness/Liveness Probes

Many CrashLoopBackOff issues happen because:

* Initial delay is too low.
* Application startup takes longer.
* Incorrect health endpoint.



### Step 6 – Check Resource Usage

```bash
kubectl top pod
```

Verify:

* CPU
* Memory
* OOMKilled
* Resource limits



### Step 7 – Check Recent Deployment

```bash
kubectl rollout history deployment <deployment>
```

If the issue started after deployment, verify:

* Image tag
* Deployment configuration
* Recent code changes



If required, I would rollback to the last stable version while continuing RCA to minimize production impact.

* Environment variables

Only after identifying the root cause would I apply the fix and validate connectivity before closing the incident.



# Question 28

### **Question:**

**Suppose your Terraform state file becomes corrupted. How would you recover it?**

### **Answer:**

First, I would stop any further Terraform operations to avoid additional inconsistencies.

My recovery approach would be:

1. Verify whether the remote state in **S3** is actually corrupted.
2. Restore the latest valid version using **S3 Versioning** if available.
3. Verify the integrity of the recovered state.
4. If recovery isn't possible, use:

```bash
terraform import
```

to reconstruct the state by importing existing AWS resources.

5. Run:

```bash
terraform plan
```

to verify Terraform correctly matches the actual infrastructure.

Only after confirming there are no unexpected changes would I proceed with:

```bash
terraform apply
```

The key objective is to recover the state without recreating production infrastructure.

# Question 30

### **Question:**

**How do you prevent or avoid Terraform state corruption and similar problems?**

### **Answer:**

To avoid Terraform state issues, I follow several best practices:

* Store the state in a **remote backend (S3)**.
* Enable **DynamoDB state locking** to prevent concurrent updates.
* Enable **S3 Versioning** for rollback and recovery.
* Restrict direct access using **IAM policies**.
* Avoid manual modifications to the state file.
* Never run parallel `terraform apply` operations on the same workspace.
* Use CI/CD pipelines to execute Terraform consistently.
* Review `terraform plan` before every apply.
* Keep regular backups of the state.
* Use reusable modules and maintain version control for Terraform code.

Following these practices significantly reduces the chances of state corruption and keeps infrastructure changes predictable and auditable.

# Question 36

### **Question:**

**Can you write a Python program to solve the following problem: Find the shortest unique prefix for each word in a given array?**

### **Answer:**

Yes. During the interview, I wrote a working brute-force solution and corrected a small typo while debugging. In a real interview, I would explain both the approach and its complexity.

```python
def shortest_unique_prefix(words):
    result = []

    for word in words:
        prefix = ""

        for ch in word:
            prefix += ch

            count = 0
            for w in words:
                if w.startswith(prefix):
                    count += 1

            if count == 1:
                result.append(prefix)
                break

    return result


words = ["zebra", "dog", "duck", "dove"]
print(shortest_unique_prefix(words))
```

### Explanation

* Iterate through each word.
* Build the prefix one character at a time.
* Count how many words start with that prefix.
* If only one word matches (`count == 1`), that prefix is unique.
* Store the prefix and continue with the next word.

### Complexity

* **Time Complexity:** **O(N² × L)**, where:

  * **N** = Number of words
  * **L** = Average word length

### Optimization

For very large datasets, I would recommend using a **Trie (Prefix Tree)**. A Trie reduces the lookup time and is the preferred production solution for shortest unique prefix problems because it avoids repeatedly scanning the entire list for every prefix.
